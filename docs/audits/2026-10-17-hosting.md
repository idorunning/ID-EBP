# Hosting and deployment audit — 17 October 2026

## Scope and judgement

Read-only inspection of the live ID-EBP Cloudflare Worker, domain settings, Supabase project metadata, database permissions, migration history and aggregate queue health. No production settings or records were changed, no users were created, no email was sent, and no public load test was run. Credentials, secret values and personal records were not retrieved.

**Deployment readiness: 6/10.** The core services and scheduled work are connected, but transport hardening, deployment automation, authentication capacity checks and recovery acceptance remain incomplete. This is an engineering judgement, not a security certification. Local fixes elsewhere in this PR are not evidence that production has been updated.

Evidence labels below distinguish **observed** configuration or results from **inferred** risks. Findings describe the live state inspected on 17 October; recheck them before deployment.

- Aggregate maintenance state showed 115 sources, all checked, no overdue checks and no stale leases. The latest completed check was 16 October at 21:30 UTC.

## Migration parity and local correction

The first ten local migration filenames used timestamps different from the hosted migration history, although names matched. The final three existing timestamps already matched. This can confuse migration tooling even when the deployed schema is correct.

Verification used only migration metadata and hashes:

```sql
select version, name,
       md5(array_to_string(statements, E'\n')) as statement_md5,
       octet_length(array_to_string(statements, E'\n')) as sql_bytes
from supabase_migrations.schema_migrations
order by version;
```

Each value was compared with the MD5 and byte length of the corresponding local SQL file. **All 13 pre-existing SQL bodies matched exactly.** MD5 was used for accidental-difference detection, not as a security signature. No database migration SQL containing runtime values was downloaded.

## Authentication burst prerequisites

Before claiming support for a launch with many simultaneous logins:

1. Record actual Supabase Auth quotas, Cloudflare Workers limits and email sending limits. Keep provider credentials and configuration values out of the report.
2. Decide whether to preserve the end-user IP for upstream Auth throttling. Current Supabase documentation requires **all three** of: a modern `sb_secret` API key, Auth's `security_sb_forwarded_for_enabled` setting enabled, and the `Sb-Forwarded-For` request header. Legacy `anon` and `service_role` JWT keys do not support this feature.
3. If implemented, obtain the IP only from the trusted Cloudflare request path and authenticated proxy context. Discard client-supplied forwarding headers; do not trust an arbitrary browser header. Never move a secret API key into browser code.
4. Exercise an isolated hosted staging environment with synthetic users: different users, a shared office/NAT IP, repeated requests from one user, simultaneous token refresh, provider throttling and provider timeouts. Do not use production accounts or send real mail during a synthetic test.
5. Record request rates, concurrency, test duration, p50/p95/p99 latency, error/429 rates, database connections and queue delay. Agree acceptance thresholds for expected use before interpreting the result. A passing local test or a connection-count snapshot does not establish hosted capacity.

The application's own IP limit and Supabase's upstream limit are separate controls. Raising one is not evidence that the other can handle a higher rate.

## Deployment runbook

1. **Freeze the reviewed release.** Use a named commit, a clean checkout and the lockfile. Run `npm ci` and `npm test`; the test script builds the Worker. Review the resulting migration, Edge Function and Worker together. Record the test output and commit.
2. **Confirm recovery prerequisites.** In the provider dashboard, verify a recent successful database backup and its retention. Record recovery objectives and a named operator. Preserve the previous Worker/Edge versions and required runtime bindings without exporting their secret values.
3. **Reconcile migration history.** Compare the corrected local versions with the hosted list. The 13 existing migrations should already be applied; only genuinely new migrations should be pending. Do not reapply renamed migrations or use a destructive reset to clear drift.
4. **Release the coordinated components.** Follow the compatibility order documented for the reviewed migration and API changes. For this release, apply the new database migration before the updated Edge Function and Worker. Preserve custom proxy authentication, session encryption configuration, email restrictions and schedules. Do not assume a GitHub push performs these actions: no Cloudflare Git connection existed at audit time.
5. **Establish deployment automation separately.** If connecting `idorunning/ID-EBP` to Cloudflare Builds, select the intended production branch, configure tests as a required build gate, use scoped deployment credentials and review whether creating the connection triggers an immediate deploy. Ensure feature branches cannot publish to the production domains. Database and Edge deployment still need an explicit coordinated process.
6. **Verify the released service.** Check apex HTTPS, HTTP/www redirects, HSTS, public directory/status responses and expected cookie/cache/security headers. Verify direct unauthorised Edge/internal requests fail. Confirm the installed migration and deployed versions, then rerun security/performance advisors. Use a separately authorised test account/mailbox for real authentication and workflow-email acceptance; no such messages were sent in this audit.
7. **Observe the first scheduled run.** Confirm the cron remains present, maintenance jobs finish, and no stale leases or growing failed/uncertain email backlog appears. An empty queue alone is not an email delivery test. Configure operational alerts for sustained API failures, unusual throttling, overdue maintenance and held deliveries; sampled logs alone are not an alerting system.
8. **Recover deliberately if needed.** Stop rollout when acceptance fails. Restore compatible previous application versions where possible. Do not automatically reverse a database migration after users have written new data. Use the reviewed forward-fix or recovery procedure and record any data-loss window.

Transport/auth configuration changes are separate from code deployment: verify TLS 1.2 minimum and leaked-password protection after changing them. HSTS supplied by the new Worker must also be checked on live HTTPS responses.

## Backup acceptance and remaining limits

A backup is not accepted as recoverable merely because the plan includes backups. Verify the latest successful backup, restore it into an isolated destination using the supported provider procedure, and check schema, permissions, representative source data, authentication recovery and application compatibility. Record achieved recovery time and data-loss window. Do not restore over production for an exercise.

Database backups do not include Storage object contents, deployed code or all external platform settings. If those services are used, include them in the recovery inventory. A separate destination or additional recovery feature may incur cost; no paid service or new environment was provisioned here.

Unverified: live Auth quotas and IP-forwarding configuration; actual backup inventory/PITR; dedicated session-secret configuration; sustained hosted load; end-to-end mailbox delivery; alert delivery; provider account recovery. The production acceptance task remains open until those checks have concrete evidence.
